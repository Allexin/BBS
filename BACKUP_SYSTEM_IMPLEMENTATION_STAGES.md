# Backup System — этапы реализации v1

## 1. Назначение документа

Этот документ определяет порядок реализации и приёмки v1. Он не повторяет
технические требования и алгоритмы из `BACKUP_SYSTEM_DESIGN.md`.

Каждый этап завершается отдельно принимаемым результатом. Следующий этап начинается
после приёмки предыдущего либо после явного решения продолжить с зафиксированным
дефектом. До финального этапа используются только тестовые конфигурации и тестовые
данные; production jobs не создаются.

## 2. Этапы

### Этап 0. Проверка технических возможностей

Результат:

- подготовлены изолированные тестовые данные, NTFS-том и restic-репозиторий;
- проверены VSS binding, чтение snapshot и удаление точного SnapshotSetID;
- проверены идентификация тестового диска, цикл online/mount/offline и восстановление
  mount point через выбранный Windows API;
- проверены backup, check и restore закреплённой версии restic с Unicode, кириллицей,
  emoji, длинными путями и открытыми файлами;
- проверены стабильный backup namespace, машинно-разбираемый fail-fast и поведение при
  принудительном прерывании;
- результаты, ограничения и воспроизводимые команды PoC зафиксированы в репозитории.

Приёмка:

- VSS snapshot позволяет прочитать контрольный файл и удаляется без orphan;
- restic не сохраняет VSS device prefix или временный mount point в backup namespace;
- ошибки источника и репозитория распознаются достаточно рано для требуемого fail-fast;
- backup/check/restore завершаются успешно, а восстановленные данные совпадают по хешам;
- после прерывания состояние тестового диска и репозитория можно однозначно проверить
  и безопасно восстановить;
- операции с физическим диском выполняются только на выделенном тестовом носителе с
  явно подтверждённым идентификатором;
- неуспешный обязательный PoC блокирует соответствующий adapter или механизм до
  принятия отдельного ADR.

### Этап 1. Каркас проекта и контракты

Результат:

- создана структура Python-проекта;
- определены конфигурационные модели, события, идентификаторы и exit codes;
- подготовлены команды manager, executor и `backupctl` без реальной backup-логики.

Приёмка:

- проект устанавливается в чистую `.venv` из lock-файла;
- все конфиги и события проходят автоматическую schema validation;
- тесты границ между manager, executor и UI проходят.

### Этап 2. Локальное состояние и управление

Результат:

- реализованы Stable/data layout, SQLite migrations и файловый spool;
- реализованы операции, runs, очередь, deduplication и локальные CLI-команды;
- история нормализованных SMART-наблюдений сохраняется для сопоставления значений и
  расчёта трендов;
- реализован JSONL-журнал и его ротация.

Приёмка:

- очередь и история корректно переживают штатный и аварийный restart;
- удаление, отмена и повторная подача операций соответствуют state machine;
- повреждённые и повторно доставленные spool-команды безопасно отклоняются;
- SMART baseline и история сравнений корректно переживают restart.

### Этап 3. Scheduler и уведомления

Результат:

- реализованы cron, job cycle, deadline-индикация и startup reconciliation;
- реализованы суточный отчёт и немедленные Telegram-alerts;
- внешние сбои Telegram не влияют на выполнение jobs.

Приёмка:

- тестовые часы подтверждают отсутствие catch-up и автоматических retry;
- cycle продвигается только при разрешённых terminal results;
- overlap, missed operations и ошибки формируют ожидаемые отчёты без дублей;
- новый регресс ключевого SMART-показателя немедленно оповещается один раз, а
  неизменное значение не создаёт дубль после следующего сбора или restart.

### Этап 4. Read-only Web UI

Результат:

- manager публикует status, health и санитизированные log projections;
- реализованы Status UI и отдельный Logs UI;
- подготовлена примерная read-only конфигурация nginx.

Приёмка:

- UI показывает jobs, активную работу, очередь, progress, диски и тома;
- UI показывает предыдущее значение, последнюю дельту и тренды ключевых
  SMART-показателей за 24 часа и 30 дней;
- Logs UI соответствует правилам ручного обновления и фильтрации;
- public tree не содержит путей, секретов и управляющих интерфейсов;
- принудительное завершение publisher не оставляет повреждённый JSON.

### Этап 5. Windows lifecycle

Результат:

- реализованы идентификация дисков, online/offline lifecycle и safety latch;
- реализованы SMART preflight и VSS adapter;
- результаты этапа 0 закреплены автоматическими integration и hardware tests.

Приёмка:

- неверный диск блокируется до изменения его состояния;
- VSS snapshot читается и удаляется без orphan;
- аварийное завершение приводит к предсказуемому recover-состоянию;
- неподтверждённый offline блокирует очередь;
- последовательные SMART-наблюдения обнаруживают регресс ключевых показателей даже
  при `PASSED` overall и значениях в vendor-норме; первое наблюдение и reset counter
  не создают ложную тревогу.
- отдельная `smart-test` job запускает разрешённый short/long self-test без изменения
  storage topology или disk lifecycle и сохраняет его итоговый результат.

### Этап 6. Mirror adapter

Результат:

- реализованы scan, plan, capacity preflight, копирование с подменой и catalog;
- реализованы удаления, crash recovery и mirror verification;
- реализован manual mirror repair.

Приёмка:

- тестовый mirror точно соответствует source с учётом excludes;
- сбой в каждой контрольной точке восстанавливается в определённое состояние;
- ошибки чтения, записи и нехватка места немедленно останавливают работу;
- полный check обнаруживает все внесённые тестовые повреждения.

### Этап 7. Snapshot adapter

Результат:

- реализованы restic backup, retention, check и prune;
- реализованы оба предусмотренных режима repository password;
- результаты restic полностью переводятся в общий event/error contract.

Приёмка:

- backup и retention проходят на тестовом repository;
- check cycle и scrub cursor повторяются после ошибки и продвигаются после успеха;
- повреждение repository обнаруживается и блокирует следующий backup;
- fail-fast поведение подтверждено интеграционными тестами.

### Этап 8. Restore

Результат:

- реализован restore для mirror и snapshot;
- реализованы target validation, incomplete marker, progress и полная read-back
  verification;
- реализованы правила очереди и уведомлений restore.

Приёмка:

- отдельный файл, поддерево и весь source восстанавливаются с правильной структурой;
- restore никогда не пишет поверх существующих данных;
- ошибка или аварийный обрыв сохраняет явно помеченный результат;
- незаметно повреждённый восстановленный файл не может дать успешный result.

### Этап 9. Windows Service и эксплуатационные сценарии

Результат:

- manager запускается через NSSM под `LocalSystem`;
- реализованы cooperative service stop, Job Object и restart policy;
- реализован validation-only запуск и Dev-to-Stable deployment tool в необходимом
  для разработки объёме.

Приёмка:

- штатный stop не применяет hard kill и завершает cleanup;
- аварийная гибель manager не оставляет orphan executor/restic;
- невалидный manager config не создаёт restart loop;
- тестовый deploy корректно останавливает и снова запускает service.

### Этап 10. Сквозная приёмка v1

Результат:

- все компоненты объединены в один тестовый Stable deployment;
- выполнены полные сценарии backup, check, failure, recover и restore;
- подготовлена эксплуатационная и disaster-recovery документация.

Приёмка:

- автоматические тесты и обязательные hardware tests проходят;
- недельный ускоренный тестовый цикл не выявляет нарушения очереди и cycle state;
- восстановление выполняется по документации на чистом тестовом окружении;
- все известные ограничения либо устранены, либо явно зафиксированы в ADR;
- система готова к отдельному этапу создания первых реальных jobs.

## 3. После v1

Инвентаризация реальных данных, выбор production-диска, настройка nginx URL,
Telegram credentials и создание production jobs выполняются только после приёмки
этапа 10 и не входят в реализацию ядра v1.
